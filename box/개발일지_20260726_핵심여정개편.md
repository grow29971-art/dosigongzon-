## 2. 안전한 복원 절차

**대원칙: 운영 데이터(Supabase 프로덕션 DB·Storage) 삭제 금지.** 복원은 코드 기준선 복귀만 의미하며, DB는 별도의 롤백 SQL(각 마이그레이션 파일 하단의 롤백 주석)로만, 그것도 데이터 파괴가 없는 경우에만 다룬다.

### 2-1. 코드 복원 (권장 순서)
```bash
# 0) 현재 상태를 먼저 보존 (어떤 경우에도 작업본을 날리지 않는다)
git branch rescue/before-restore-$(date +%Y%m%d-%H%M)

# 1) 태그 기준 복원 브랜치 생성 후 확인

npx tsc --noEmit && npm run build   # 기준선이 정상 빌드되는지 확인

# 2) 문제 커밋만 되돌릴 수 있으면 revert 우선 (히스토리 보존)
git checkout main
git revert <문제 커밋>...

# 3) 전체 복귀가 불가피할 때만 (원격 히스토리 덮어쓰기 — 최후 수단)
```

## 5. Feature flag / Kill switch 설계 원칙

### 원칙
1. **기본값 off** — flag 미설정·판독 실패 시 무조건 기존 동선으로 동작 (fail-closed).
2. **단계당 flag 1개** — 여러 변경을 한 flag에 묶지 않는다. 끌 때 무엇이 꺼지는지 명확해야 한다.
3. **kill switch = 환경변수** — Vercel Dashboard에서 값 변경 + 재배포만으로 코드 revert 없이 즉시 차단 가능해야 한다.
4. **DB 스키마와 분리** — flag를 꺼도 스키마·데이터는 건드리지 않는다. 롤백 부담 최소화.
5. **flag 제거는 P8에서만** — 안정화 판정 전에는 코드에서 flag 분기를 지우지 않는다.
6. 클라이언트 노출이 필요한 flag만 `NEXT_PUBLIC_` 접두어 사용, 서버 전용 판단은 접두어 없이.
