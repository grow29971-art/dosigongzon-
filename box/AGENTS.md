# box/ — SQL 마이그레이션·개발일지 보관함

## 범위

빌드에 포함되지 않는 보관함. ① DB 마이그레이션·시드 SQL ② 개발일지 ③ 기획·체크리스트 문서.
앱 코드를 여기 두지 않는다.

## 파일 네이밍

- 마이그레이션: `supabase_[기능명]_migration.sql` / 시드: `supabase_[기능명]_seed.sql`
- 개발일지: `개발일지_YYYYMMDD.md`
- 실행 순서가 중요한 묶음은 RUN_ORDER 문서로 순서를 못 박는다.

## 마이그레이션 SQL 작성 규칙

- 머리: 목적·증상·원인 요약 + "실행 위치: Supabase Dashboard → SQL Editor" + "⚠ Chrome 번역 OFF".
- 본문: `create table if not exists` / `alter table ... add column if not exists` 멱등 패턴.
  새 테이블은 RLS 활성화 + SELECT/INSERT/UPDATE/DELETE 정책을 같은 파일에 포함.
- 꼬리: 실행 후 검증 쿼리 + **롤백 SQL(주석)**. 롤백 없는 마이그레이션은 미완성이다.
- 함수·트리거 교체는 `create or replace`로, 이전 버전으로 되돌리는 방법(어느 파일의 어느 블록을
  재실행하면 되는지)을 롤백 주석에 명시.

## 실행·검증 절차

1. 파일 작성 → 커밋(코드와 별도 커밋 가능) → 사장님에게 실행 요청.
2. 사장님이 SQL Editor에서 실행(에이전트가 DB에 직접 DDL을 실행하지 않는다).
3. 실행 후 REST 프로브로 실측 검증 — "실행했다"는 말도, 과거 문서의 "실행 대기" 표기도 믿지 않고
   테이블·행·함수 존재를 직접 확인한다.

## 개발일지

- 굵직한 작업일마다 `개발일지_YYYYMMDD.md`로 남긴다(무엇을·왜·결과). 과거 일지는 수정하지 않는다
  — 당시 판단의 기록이다.

## 이 폴더에서 하지 않는 것

- 오래된 SQL 파일 삭제 금지 — 실행 이력의 유일한 재현 수단이다(삭제 가드 훅이 걸려 있다).
- 파일 내용을 소급 수정해 "이미 실행된 SQL"과 파일을 다르게 만들지 않는다. 수정이 필요하면
  새 마이그레이션 파일을 추가한다.
