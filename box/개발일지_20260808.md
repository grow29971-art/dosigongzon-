> 기능 하나에 집중한 날. "고양이가 죽으면 지도에서 삭제하지 말고 고양이별로 보내자,

> 원칙 유지: 프로덕션 DB 직접 쓰기는 box/*.sql로 기록, 매 커밋 tsc, 실측은 REST 프로브.

## 1. 왜 만들었나 — 삭제가 기록까지 지우고 있었다

요청은 정서적인 것이었지만, 코드를 열어보니 **실제 결함 두 개** 위에 얹힌 요청이었다.

**(1) `deleteCat`은 hard DELETE다.**
`care_logs`가 `ON DELETE CASCADE`라 아이를 지우는 순간 그 아이를 돌본 기록이 통째로 사라진다.
`cat_cards`·댓글도 같이 간다. 돌보던 사람 입장에선 두 번 잃는 일이었고, 되돌릴 방법이 없었다.

**(2) 떠난 아이에게 건강경보가 무한 반복되고 있었다.**
`health-alert-push` 크론은 `hidden=false` + `health_status in (caution, danger)`를 집어간다.
`health_status`는 자동 해제가 없다. 무지개다리를 건넌 아이가 `danger`로 굳어 있으면
같은 동 이웃들에게 "N일째 안부가 없어요"가 24시간 주기로 **영구히** 나간다.
현재 대상: danger 1마리, caution 11마리.

이 둘 때문에 "삭제 대신 상태 전환"은 정서적 선택이 아니라 **필요한 수리**였다.

## 2. 설계 — 행을 남기고 상태만 바꾼다

```
cats.memorial_at   timestamptz  -- null 이면 생존
cats.memorial_note text         -- 마지막 인사
cats.memorial_by   uuid         -- 보낸 사람
```

행이 남으므로 `care_logs`·카드·댓글이 전부 보존된다. 지도·건강경보·공개 뷰에서만 뺀다.
삭제 버튼은 **지우지 않았다** — 오등록 정정에는 여전히 필요하고, 고양이별은 삭제의 대체가
아니라 별도 동선이다. 잘못 보냈으면 `/memorial`에서 지도로 되돌릴 수 있다.

`memorial_flowers`(헌화)는 계정당 1회 토글. 추모 공간의 유일한 상호작용으로 제한했다.

## 3. 마이그레이션 3연속 실패 — 전부 내 SQL 문제

| # | 에러 | 원인 |
|---|---|---|
| 1 | `42P16: cannot change name of view column "lat" to "art_key"` | `create or replace view`는 **기존 컬럼 순서를 못 바꾼다.** 현재 `cats_public_map`은 `art_key`·`art_colors`가 cats에 추가되기 전에 만들어져 끝이 `cleaned_at, lat, lng`다. 컬럼을 다시 뽑으면 신규 컬럼이 lat 자리에 끼어든다 → `drop` 후 `create` |
| 2 | `42883: function public.is_user_not_suspended() does not exist` | 무인자가 아니라 `(uid uuid)`를 받는다. **CLAUDE.md에 무인자처럼 적혀 있는 걸 믿고 확인 안 한 게 원인.** `auth.uid()`를 넘겨야 한다 |
| 3 | (에러 아님, 설계 수정) | 재생성 시 `memorial_by`를 뷰에서 제외. 보낸 사람의 auth uid라 `caretaker_id` 외로 uid 노출을 넓힐 이유가 없다 |

**1번이 만든 진짜 위험은 따로 있었다.** `cats_public_map`은 8/2에
"공개 definer 뷰가 RLS를 우회해 anon 키만으로 전 고양이 이름 변조·대량 DELETE가 실제로
커밋됐던" 그 뷰다(`box/supabase_public_view_write_revoke_migration.sql`).
**drop하는 순간 그때 걸어둔 revoke가 같이 날아간다.**
마이그레이션에 재생성 직후 revoke를 다시 걸도록 넣고, 실행 후 anon 키로 재검증했다.

```
anon PATCH like_count → 401
anon PATCH name       → 401
anon DELETE           → 401
```

빈 body PATCH는 권한 검사 전에 204를 뱉으므로(7/31에 겪은 오탐) **반드시 컬럼을 지정해**
프로브했다.

실행 후 실측: cats 245 · 공개 뷰 229(변동 없음) · 좌표 지터 유지(base ≠ view).

## 4. 무지개다리 애니메이션 — 1차는 버렸다

처음엔 사진이 위로 떠오르며 별이 되는 장면을 만들었는데 "장면도 너무 구리다,
무지개다리를 건너는 애니메이션이었으면 좋겠다"는 피드백을 받고 전면 교체했다.

- SVG 곡선 위에 7색 다리를 아래에서 위로 한 겹씩 그린다(`stroke-dashoffset`)
- 고양이가 **`offset-path`로 그 곡선을 실제로 걷는다** — 다리 곡선(`BRIDGE`)과
  걷는 경로(`WALK`)가 같은 수식이라 정확히 다리 위를 지나간다. translate 흉내가 아니다
- 걸음에 맞춘 상하 흔들림, 지나간 자리의 발자국, 다리 끝의 빛

**소리는 Web Audio로 합성했다 — 오디오 파일 없음.**
오르골 느낌의 5음계 상행(사인 기음 + 배음 2개, 지수 감쇠)이 건너는 동안 한 음씩 오르고,
다 건널 때 종이 울린다. 밑에 밴드패스 화이트 노이즈로 바람결을 깔았다.
외부 에셋을 안 쓴 이유는 CSP 화이트리스트·앱 용량·저작권이 전부 따라붙는데
이 한 장면에만 쓰이기 때문이다. 클릭 제스처 직후 `AudioContext`를 만들어 자동재생 정책을 통과한다.

우상단 토글로 끌 수 있고 `localStorage`에 기억한다.
`prefers-reduced-motion`이면 애니메이션도 소리도 건너뛴다.

## 5. 추모관 — 돌봄 기록 전부

`/memorial/[id]`. 삭제가 아니라 상태 전환이라 `care_logs`가 남아 있어서 가능한 화면이다.

- 상단 요약: "N명이 M번 돌봤어요" + 많이 한 돌봄 4종
- 날짜별로 묶인 **전체 돌봄 기록** — 종류·양·메모·사진·시각·작성자
- 헌화(계정당 1회), 등록자에게만 되돌리기

목록(`/memorial`)에는 "고양이별은 어떤 곳인가요?" 접이식 안내를 붙였다.
아이가 없을 땐 펼친 채로, 있을 땐 접어서 목록을 먼저 보여준다.
**"삭제와 무엇이 다른가요"를 굵게 적었다** — 이걸 모르면 아이를 지워버리게 되고 그건 복구가 안 된다.

진입 경로는 지도 우측 FAB 스택 맨 위(별 아이콘, 밤하늘 톤)와 마이페이지 메뉴 두 곳.

예전처럼 구조적으로 못 찍는 상태가 아니다. 다만 **17은 표본이 작다.**
진짜 전환율이 12%여도 17명 중 0명일 확률이 약 12%다. 아직 "설득 실패"로 단정할 수 없다.

### 알려진 잔재

**되돌리기(`restoreCatFromStar`)는 `memorial_flowers`를 지우지 않는다.**
헌화 삭제는 RLS상 헌화한 본인만 가능해서 클라이언트가 남의 헌화를 못 치운다.
되돌린 뒤 다시 보내면 예전 헌화 수가 되살아난다.
이번엔 서비스키로 같이 지웠다. 되돌리기 자체가 드문 동작이라 지금 고칠 일은 아니고,
실사용에서 걸리면 "등록자는 `memorial_at`이 null인 자기 고양이의 헌화를 삭제할 수 있다"
정책 한 줄이면 된다.
