## 1. 환불 정책 (전자상거래법 제17조)

구현: `lib/refund-policy.ts` — 순수 함수. 유저 화면·서버 API·관리자 화면이 **모두 이 함수를 공유**한다.
값은 `/shop/policy` 고지 문구와 일치시켰다 (한쪽만 고치면 그 자체가 법 위반 소지).

### 기간

| 사유 | 기한 | 기산점 |
|---|---|---|
| 단순변심 (`change_of_mind`) | **7일** | 공급받은 날 = `delivered_at` → 없으면 `shipped_at` → 없으면 `paid_at` |
| 판매자 귀책 (`defect`·`wrong_delivery`·`delayed`·`out_of_stock`) | **90일** | 동일 |

기산점 기록이 아예 없으면 **거부하지 않고 심사로 넘긴다.** 데이터 부재를 유저 불이익으로 돌리지 않는다.

### 배송 단계별

| 주문 상태 | 가능 | 처리 | 반품 배송비 |
|---|---|---|---|
| `pending` | ❌ | 환불이 아니라 주문 취소 경로 | — |
| `paid` · `preparing` | ✅ | **즉시 자동환불** (전액) | 없음 |
| `shipping` | ✅ | **관리자 심사** (회수 필요) | 단순변심 3,000원 / 귀책 0 |
| `delivered` | ✅ 기한 내 | **관리자 심사** (반품 도착 확인) | 단순변심 3,000원 / 귀책 0 |
| `cancelled` · `refunded` | ❌ | 종착 | — |

> `preparing`을 포함시킨 것이 기존 대비 변경점이다. 정책 페이지는 "배송 시작 전 주문은 주문
> 상세에서 직접 취소"라고 고지하는데 기존 UI는 `paid`에서만 버튼을 노출했다(`shop/orders/[id]/page.tsx:264`).
> **고지와 구현이 어긋나 있던 것을 정책 쪽에 맞춰 정정.**

### 상품 유형별

| 유형 | 재고 복원 | 후원 집계 | 특이사항 |
|---|---|---|---|
| 실물 | **필요** (`increment_product_stock`) | 해당 시 차감 | 회수 절차 필요 |
| 가상 (`is_virtual`) | 불필요 | 해당 시 차감 | 배송 개념 없음 → **항상 즉시 환불**. 단 결제 후 7일 제한 |
| 후원 (`is_donation`) | 실물 여부 따름 | **반드시 차감** | 공개 후원 집계 = 투명 정산의 근거라 무결성 필수 |

### 배송비 부담

- 단순변심 → **구매자**. 환불액에서 반품비 3,000원 차감 (배송 전이면 회수할 물건이 없어 0원).
- 하자·오배송·지연·품절 → **판매자**. 차감 없이 전액 환불.

## 2. 상태 머신

**환불 축을 `orders.status`에서 분리했다.** 지시받은 원안(`paid → refund_requested → ...`)을 따르지 않은 이유:

1. `status` CHECK가 **결제 단계와 배송 단계를 한 컬럼에** 담고 있다
   (`pending, paid, preparing, shipping, delivered, cancelled, refunded` — `supabase_shop_migration.sql:72-73`).
   여기에 `refund_requested`를 넣으면 "배송완료 상태에서 환불요청"을 표현할 수 없고, 반려 시 돌아갈 곳이 없다.
2. `guard_order_status_transition()` 트리거가 **service_role 포함 모든 경로**에 전이표를 강제하고
   `cancelled`/`refunded`는 **종착역**이다(`supabase_orders_status_guard_migration.sql:32-45`).
   즉 "요청 → 반려 → 원상복귀"가 물리적으로 불가능하다.

분리한 결과 **트리거를 전혀 수정할 필요가 없다.**

```
[결제·배송 축]  orders.status
    pending ──> paid ──> preparing ──> shipping ──> delivered
                  └─────────┴───────────┴──────────┴──> refunded  (전액환불 완료 시에만)
                  └──> cancelled                              ※ 기존 트리거가 허용하는 전이 그대로

[환불 축]  orders.refund_status                    ← 위 축과 독립적으로 움직임
    none ──> requested ──> (승인) ──> refunded | partial_refunded
                      └──> rejected ──> none 으로 되돌릴 수 있음(트리거 없음)
                  ※ 즉시환불(mode=auto)은 requested를 건너뛰고 바로 refunded
```

- `refund_status`만 바꾸는 UPDATE는 `old.status = new.status`라 트리거 28-30행에서 통과.
- 전액환불 완료 시의 `status → refunded` 전이는 트리거 34-37행이 이미 허용.
- `refunded`는 대사 크론의 `CANCELLED_LIKE`에도 포함돼 있어 기존 대사 로직과도 정합.

## 3. 스키마 — `box/supabase_refund_system_migration.sql`

| 테이블 | 추가/신설 | 목적 |
|---|---|---|
| `orders` | `refund_status`, `refund_amount`, `refund_requested_at`, `refunded_at`, `refund_reason`, **`shipped_at`, `delivered_at`** | 환불 축 + 청약철회 기산점 |
| `order_items` | `refunded_quantity`, `donation_refunded` | 품목별 환불 수량·후원 차감 |
| `order_refunds` | 신설 | 환불 원장(감사 추적) + 멱등 키 |
| `order_refund_items` | 신설 | 부분환불 대상 품목 |
| `donation_totals` | 신설(뷰) | 후원 집계에서 환불분 차감 |

### DB가 직접 막는 것 (앱 버그가 나도 뚫리지 않는 방어선)

```sql
orders.refund_amount  >= 0 and <= payment_amount          -- 과잉 환불
order_items.refunded_quantity >= 0 and <= quantity        -- 재고 이중 복원
order_items.donation_refunded >= 0 and <= donation_amount -- 후원 집계 음수화
order_refunds.idempotency_key  UNIQUE                     -- 이중 환불 호출
order_refunds  부분 유니크 인덱스 (status in requested/approved) -- 주문당 열린 요청 1건
```

### 멱등성 설계

`order_refunds.idempotency_key`(unique)를 **토스 `Idempotency-Key` 헤더와 같은 값**으로 쓴다.
토스는 같은 키면 실제 요청 없이 첫 응답을 그대로 반환한다(최대 300자·15일 유효, 공식 문서 확인).
따라서 **"우리 DB에 행이 있다 = 토스에도 이미 갔다"** 가 성립해 이중 청구가 구조적으로 불가능하다.
여기에 기존 코드의 조건부 상태 전환 패턴(`.eq("status", ...).select("id")`으로 0행/1행 판별)을
그대로 재사용해 후처리(재고·포인트)는 "이긴 요청"만 수행한다.

### 포인트 이중반환 — 가장 위험한 지점

`point_ledger`의 `unique(user_id, reason)`이 **유일한 방어선**이다.
기존 취소 경로 2개가 같은 reason `order-cancel:{orderId}`를 쓴다(`cancel/route.ts:159`, `webhook/route.ts:294`).
새 환불 경로가 다른 reason을 쓰면 **같은 주문이 포인트를 두 번 돌려받는다.**

→ `pointRefundReason()`으로 규약을 박제했다. **전액환불은 기존과 동일한 문자열**을 써서 충돌시키고,
부분환불만 `order-refund:{refundId}`로 분리한다(여러 번 일어날 수 있으므로).
