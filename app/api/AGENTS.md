# app/api/ — 서버 엔드포인트

## 범위

인증 콜백, 크론, 결제, 푸시, 챗봇, 검증 프록시 등 서버 전용 로직. 화면 렌더링과 클라이언트
상태는 소관 밖. 여기만이 service_role 클라이언트(`lib/supabase/service.ts`)를 쓸 수 있는 영역이다
— 단 반드시 호출자 검증 후에.

## 모든 라우트의 기본 골격

1. **인증**: 유저 라우트는 Bearer 토큰 또는 세션으로 `auth.getUser()` 확인. 크론 라우트는
   `CRON_SECRET` 검사. 무인증 라우트는 명시적 사유가 있을 때만(로그 적재 등)이고 rate limit 필수.
2. **rate limit**: 쓰기·발송 계열은 `lib/rate-limit.ts`로 유저 단위 제한(인메모리라 느슨함 전제).
3. **권한 검증**: service 클라이언트로 조회하기 전에, 호출자가 그 자원에 대한 권한이 있는지
   직접 확인한다(RLS를 우회하는 순간부터는 코드가 곧 정책이다).
4. **응답**: 성공 `{ ok: true, ... }`, 실패 `{ ok: false, error }` + 상태코드. 에러에 스택·쿼리·
   내부 식별자 노출 금지.

## 다중 수신 푸시 라우트 (스팸·위조 벡터)

여러 명에게 알림을 뿌리는 라우트는 추가로: 호출자가 알림의 **근거 행위를 실제로 했는지** 서버가
검증해야 한다(서클 멤버 여부, 5분 내 실기록 존재 등). 기준 구현:
`circle/notify-message`, `cats/notify-watchers`. 발송 중 410/404 구독은 그 자리에서 삭제.

## 크론 라우트

- 실패를 200으로 감싸 반환하지 않는다 — 결행이 성공으로 위장돼 은폐된 사고가 있었다.
- `maxDuration`은 라우트별 독립 설정(공유 상수로 묶지 말 것 — 커플링 사고 이력).

## 결제 라우트

- `PAYMENT_ENABLED` 게이트가 꺼진 상태가 기본. 게이트를 켜는 조건(라이브 키·웹훅 시크릿·D-day
  체크)은 사장님 결정 사안이며 코드에서 임의로 켜지 않는다. 금액은 서버 재계산 — 클라이언트가
  보낸 금액을 신뢰하지 않는다.

## 테스트 관점

- 배포 후 무인증 호출이 401/403으로 막히는지 curl로 실측하는 것까지가 라우트 추가의 완료 조건.
- 인증 실패 경로(`auth_error_logs` 적재)는 절대 예외를 밖으로 던지지 않는다 — 로깅 실패가
  로그인 실패를 만들면 안 된다.
